# Лабораторная работа 10. Послойная диагностика недоступного сетевого сервиса

[Подготовка, пакеты, полные конфиги и уточнения](README.md) · [Общие материалы и ключи](../../PREPARATION.md)

Ниже все шаги руководства лабораторных v4 от 10.08.2026 с сохраненными
командами и ожидаемыми результатами. Сначала выполните подготовку в README:
она определяет адреса, значения переменных и различия ОС. Команды выполняются
по одной, на указанной машине; альтернативные ветки ОС не выполняются вместе.
В командах по умолчанию X=10/Y=20/Z=30, lab NIC=enp0s8, зоны internal/external/public.
Их необходимо сопоставить с реальными NIC/zone по README. Имена unit и web-user
по умолчанию Rocky; для Debian/Ubuntu используйте соответствия из README.
Выводы — образцы, а не протокол запуска на вашей ВМ.

Цель лабораторной работы: локализовать неисправность от адреса и маршрута до DNS, listener, firewall, TLS и прикладного HTTP-ответа.

Стенд: подготовленный преподавателем TLS-сервис app.example.test:8443, сервер 192.168.10.10 с firewalld и клиент 192.168.10.100; внесен один дефект. X заменяется фактическим номером подсети.

Сценарий: преподаватель вносит одну неисправность в доступ к TLS-сервису. Слушатель локализует ее последовательно на уровнях адресации, маршрута, DNS, порта и TLS.

Планируемый результат: для выданного преподавателем дефекта названы нарушенный слой, подтверждающая команда и минимальное исправление; после исправления endpoint проходит end-to-end тест.

## Ограничения и безопасность

Важно: не меняйте конфигурацию до фиксации симптомов.

Важно: tcpdump запускайте с фильтром и ограничением count, чтобы не собрать чужой трафик.

## Ход выполнения

## Шаг 1. Выполнить прикладной HTTP-запрос

**Зачем: Зафиксируйте точную ошибку клиента, затем проверьте локальный адрес и выбранный route. Отправьте прикладной HTTP/HTTPS-запрос. Параметры --resolve/--cacert проверяют нужный адрес, имя и доверие без отключения TLS-проверок.**

```bash
curl -v --connect-timeout 4 https://app.example.test:8443/ -o /dev/null
```

Ожидаемый вывод и результат:

```text
Зафиксирован конкретный симптом: successful HTTP response, no route, timeout, connection refused либо ошибка TLS/HTTP. До исправления exit status может быть ненулевым.
```

## Шаг 2. Проверить сетевую конфигурацию

**Зачем: Проверяем состояние сетевых интерфейсов, чтобы исключить отключенный линк до диагностики адресов и маршрутов.**

```bash
ip -br link
```

Ожидаемый вывод и результат:

```text
<интерфейс> UP <адрес>/<prefix>
```

## Шаг 3. Проверить сетевую конфигурацию

**Зачем: Проверяем адреса и состояние интерфейсов клиента, чтобы исключить локальную сетевую проблему до тестирования приложения.**

```bash
ip -br address
```

Ожидаемый вывод и результат:

```text
<интерфейс> UP <адрес>/<prefix>
```

## Шаг 4. Проверить сетевую конфигурацию

**Зачем: Проверяем таблицу маршрутов, чтобы обнаружить отсутствие шлюза или маршрута к серверной сети.**

```bash
ip route
```

Ожидаемый вывод и результат:

```text
<сеть> via <gateway> dev <интерфейс>
```

## Шаг 5. Проверить сетевую конфигурацию

**Зачем: Уточняем выбранный ядром маршрут и исходный адрес именно для диагностируемого сервера.**

```bash
# 192.168.10.10 — адрес диагностируемого сервера
ip route get 192.168.10.10
```

Ожидаемый вывод и результат:

```text
<сеть> via <gateway> dev <интерфейс>
```

## Шаг 6. Проверить IP-доступность узла

**Зачем: Проверяем базовую ICMP-достижимость сервера; успешный ping не доказывает доступность TCP-порта приложения.**

```bash
# 192.168.10.10 — адрес диагностируемого сервера
ping -c 2 192.168.10.10
```

Ожидаемый вывод и результат:

```text
Получены ICMP-ответы либо зафиксирована потеря пакетов. Отсутствие ICMP само по себе не доказывает недоступность TCP-сервиса.
```

По сообщениям клиента различаются no route, timeout, refused и TLS/HTTP error.

## Шаг 7. Проверить разрешение имени через NSS

**Зачем: getent показывает взгляд системного resolver, dig — конкретного DNS. nc проверяет только установление TCP. Разрешите имя через системный NSS, то есть тем же путем, которым пользуются прикладные программы, а не только утилита dig.**

```bash
getent ahostsv4 app.example.test
```

Ожидаемый вывод и результат:

```text
<адрес> STREAM <имя>
...; exit status = 0
```

## Шаг 8. Проверить DNS-запись

**Зачем: Проверяем A-запись непосредственно на DNS-сервере стенда, чтобы отделить ошибку зоны от локального NSS или кэша клиента.**

```bash
# 192.168.10.53 — DNS-сервер стенда
dig @192.168.10.53 app.example.test A +noall +answer
```

Ожидаемый вывод и результат:

```text
<имя>. <TTL> IN <тип> <ожидаемое значение>
```

## Шаг 9. Проверить доступность TCP-порта

**Зачем: Проверяем установление TCP-соединения с портом приложения отдельно от HTTP и TLS.**

```bash
nc -vz -w 3 app.example.test 8443
```

Ожидаемый вывод и результат:

```text
Connection to <host> <port> port [tcp/*] succeeded!
```

Адрес из DNS совпадает с ожидаемым или найден конкретный DNS-дефект.

## Шаг 10. Проверить состояние службы

**Зачем: На сервере проверьте lifecycle, effective listener и firewall. Active unit без listener не считается работающим сервисом. Команда обращается к systemd. enable управляет автозапуском, --now также меняет текущее состояние, status/show читают фактические свойства, reload применяет проверенную конфигурацию без полного restart.**

```bash
systemctl status lpic103-tls.service --no-pager
```

Ожидаемый вывод и результат:

```text
Active: active (running) ...
Loaded: loaded (...)
```

## Шаг 11. Проверить сетевой listener

**Зачем: Проверьте реальный socket, адрес, порт и процесс-владелец; состояние службы само по себе не доказывает наличие listener.**

```bash
sudo ss -lntp 'sport = :8443'
```

Ожидаемый вывод и результат:

```text
LISTEN ... <адрес>:<TCP-порт> ... users:(("<процесс>",pid=<PID>))
```

## Шаг 12. Изменить или проверить правило firewall

**Зачем: Определяем активные зоны и их привязки, чтобы анализировать правила firewall, реально применяемые к учебному трафику.**

```bash
sudo firewall-cmd --get-active-zones
```

Ожидаемый вывод и результат:

```text
success или список zone/source/service/port, соответствующий команде
```

## Шаг 13. Изменить или проверить правило firewall

**Зачем: Проверяем все зоны firewall, чтобы найти правило или привязку интерфейса, влияющие на доступ к приложению.**

```bash
sudo firewall-cmd --list-all-zones
```

Ожидаемый вывод и результат:

```text
success или список zone/source/service/port, соответствующий команде
```

## Шаг 14. Просмотреть журнал службы

**Зачем: Выберите журнал нужного unit и ограничьте временной диапазон, чтобы связать сообщение с только что выполненным действием.**

```bash
journalctl -u lpic103-tls.service --since '-10 min' --no-pager
```

Ожидаемый вывод и результат:

```text
... <unit>[PID]: <сообщение, относящееся к текущему действию> ...
```

Listener address/port и примененная zone сопоставлены с клиентским путем.

## Шаг 15. Подтвердить административные полномочия

**Зачем: Короткий capture отвечает, дошел ли SYN. Запустите его в фоне на сервере, повторите запрос с клиента, затем s_client отделит TLS от HTTP. Заранее подтвердите sudo-полномочия, чтобы запрос пароля не прервал фоновый захват трафика.**

```bash
# На сервере
sudo -v
```

## Шаг 16. Ограничить время диагностической команды

**Зачем: Записываем ограниченный по времени обмен клиента с TCP/8443, чтобы увидеть установление соединения и направление потери пакетов.**

```bash
# 192.168.10.100 — адрес клиента, который подключается к серверу
sudo timeout 15 tcpdump -l -ni any -c 20 'host 192.168.10.100 and tcp port 8443' > /tmp/lpic103-diag.pcap.txt &
```

Ожидаемый вывод и результат:

```text
<вывод ограниченной по времени команды>; exit status 0/124 согласно сценарию
```

## Шаг 17. Задать переменную текущего сеанса

**Зачем: Сохраняем PID фонового захвата, чтобы затем дождаться именно этого процесса, а не читать незавершенный файл.**

```bash
CAPTURE_PID=$!
```

## Шаг 18. Проверить TLS-соединение

**Зачем: Установите TLS-сеанс с SNI и проверкой имени; для SMTP STARTTLS явно указывается прикладной протокол.**

```bash
# На клиенте в течение 15 секунд
echo | openssl s_client -connect app.example.test:8443 -servername app.example.test -verify_hostname app.example.test -CAfile "$PKI/ca.crt"
```

Ожидаемый вывод и результат:

```text
Verify return code: 0 (ok)
```

## Шаг 19. Выполнить прикладной HTTP-запрос

**Зачем: Создаем проверяемый HTTPS-запрос во время захвата, чтобы сопоставить прикладной результат с сетевыми пакетами.**

```bash
curl --fail --cacert "$PKI/ca.crt" https://app.example.test:8443/ -o /dev/null
```

Ожидаемый вывод и результат:

```text
curl завершается с exit status = 0; тело ответа перенаправлено в указанный файл или /dev/null.
```

## Шаг 20. Дождаться фонового процесса

**Зачем: Дожидаемся окончания ограниченного захвата перед чтением результата; его статус сам по себе не заменяет анализ пакетов.**

```bash
# На сервере
wait "$CAPTURE_PID" || true
```

## Шаг 21. Сформировать или вывести контрольные данные

**Зачем: Читаем записанный обмен пакетами, чтобы определить, на каком этапе прерывается соединение.**

```bash
cat /tmp/lpic103-diag.pcap.txt
```

После минимального исправления TCP, TLS и HTTP проходят.
