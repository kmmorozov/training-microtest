# Лабораторная работа 14. Авторитетный BIND: прямая и обратная зона

[Подготовка, пакеты, полные конфиги и уточнения](README.md) · [Общие материалы и ключи](../../PREPARATION.md)

Ниже все шаги руководства лабораторных v4 от 10.08.2026 с сохраненными
командами и ожидаемыми результатами. Сначала выполните подготовку в README:
она определяет адреса, значения переменных и различия ОС. Команды выполняются
по одной, на указанной машине; альтернативные ветки ОС не выполняются вместе.
В командах по умолчанию X=10/Y=20/Z=30, lab NIC=enp0s8, зоны internal/external/public.
Их необходимо сопоставить с реальными NIC/zone по README. Имена unit и web-user
по умолчанию Rocky; для Debian/Ubuntu используйте соответствия из README.
Выводы — образцы, а не протокол запуска на вашей ВМ.

Цель лабораторной работы: создать две согласованные master-зоны, проверить их до reload и получить authoritative A, MX, CNAME и PTR ответы.

Стенд: DNS-сервер 192.168.10.53 с BIND; клиенты обращаются к нему напрямую. X заменяется фактическим номером LAN-подсети и обратной зоны.

Сценарий: для зоны example.test поднимается авторитетный DNS с прямым и обратным разрешением имен; синтаксис и серийные номера зон проверяются до reload.

Планируемый результат: named-checkconf/checkzone успешны; dig возвращает AA и непротиворечивые forward/reverse записи зоны example.test.

## Ограничения и безопасность

Важно: зона .test предназначена для тестирования и не должна делегироваться в публичный DNS.

Важно: Serial увеличивается при каждом изменении зоны.

## Ход выполнения

## Шаг 1. Установить требуемые пакеты

**Зачем: Установите authoritative DNS package своей ОС. До добавления зон узнайте service unit, пути конфигурации, адрес listener и текущую policy recursion. Установите пакеты только для выбранного семейства ОС. Ключ -y подтверждает пакетную транзакцию без дополнительного запроса.**

```bash
# RHEL-like
sudo dnf install -y bind bind-utils
```

## Шаг 2. Обновить метаданные пакетов

**Зачем: Обновите локальные метаданные репозиториев до установки пакетов; это действие не устанавливает и не обновляет сами пакеты.**

```bash
# Debian/Ubuntu — альтернатива
sudo apt update
```

## Шаг 3. Установить требуемые пакеты

**Зачем: Устанавливаем BIND и утилиты проверки DNS в Debian/Ubuntu для настройки авторитетного сервера и тестирования зон.**

```bash
# Debian/Ubuntu — альтернатива
sudo apt install -y bind9 bind9-utils dnsutils
```

## Шаг 4. Проверить версию BIND

**Зачем: Проверьте фактическую версию BIND на стенде; от нее зависят доступные директивы конфигурации и диагностические параметры.**

```bash
named -V | head -2
```

Ожидаемый вывод и результат:

```text
BIND 9.<версия> ...
```

## Шаг 5. Проверить конфигурацию DNS

**Зачем: Просматриваем разобранную конфигурацию BIND, чтобы установить действующие параметры и подключенные файлы до изменения зон.**

```bash
sudo named-checkconf -p | sed -n '1,80p'
```

Ожидаемый вывод и результат:

```text
Выведена effective-конфигурация BIND; синтаксических ошибок нет, exit status = 0.
```

## Шаг 6. Включить автозапуск службы

**Зачем: Запускаем BIND и включаем автозапуск, чтобы DNS-сервер обслуживал запросы после загрузки ВМ.**

```bash
sudo systemctl enable --now named
```

Ожидаемый вывод и результат:

```text
Created symlink ... (при первом включении); exit status = 0
```

## Шаг 7. Проверить состояние службы

**Зачем: Проверяем запуск BIND, чтобы выявить ошибку службы до проверки DNS-запросов.**

```bash
systemctl status named --no-pager
```

Ожидаемый вывод и результат:

```text
Active: active (running) ...
Loaded: loaded (...)
```

## Шаг 8. Проверить сетевой listener

**Зачем: Проверьте реальный socket, адрес, порт и процесс-владелец; состояние службы само по себе не доказывает наличие listener.**

```bash
sudo ss -lunpt 'sport = :53'
```

Ожидаемый вывод и результат:

```text
LISTEN ... <адрес>:<TCP-порт> ... users:(("<процесс>",pid=<PID>))
UNCONN ... <адрес>:<UDP-порт> ... users:(("<процесс>",pid=<PID>))
```

BIND active и слушает 192.168.10.53:53 либо ожидаемый lab interface.

## Шаг 9. Ограничить listener и отключить recursion

**Зачем: Устанавливаем полный конфиг авторитетного BIND по README, чтобы ограничить запросы учебной сетью и отключить ненужную рекурсию и передачу зон.**

Установите полный файл для этого этапа по [инструкции подготовки](README.md).

```bash
# Выберите named-rhel.conf или named-debian.conf, затем выполните:

```

Установите полный файл для этого этапа по [инструкции подготовки](README.md).

## Шаг 13. Проверить конфигурацию DNS

**Зачем: Неверная зона не должна попадать в работающий сервер. Только после трех проверок выполните reload. Выполните одну прикладную проверку сервиса и интерпретируйте ответ протокола, а не только exit status процесса.**

```bash
sudo named-checkconf
```

Ожидаемый вывод и результат:

```text
Команда не сообщает синтаксических ошибок и завершается с exit status = 0.
```

## Шаг 14. Проверить конфигурацию DNS

**Зачем: Проверяем прямую зону до загрузки в BIND, чтобы выявить синтаксические ошибки и некорректные записи.**

```bash
sudo named-checkzone example.test /var/named/db.example.test
```

Ожидаемый вывод и результат:

```text
zone <имя>/IN: loaded serial <SERIAL>
OK
```

## Шаг 15. Проверить конфигурацию DNS

**Зачем: Проверяем обратную зону до reload, чтобы PTR-записи и имя зоны соответствовали учебной подсети.**

```bash
# X — номер LAN-подсети в имени обратной DNS-зоны
sudo named-checkzone 10.168.192.in-addr.arpa /var/named/db.192.168.10
```

Ожидаемый вывод и результат:

```text
zone <имя>/IN: loaded serial <SERIAL>
OK
```

## Шаг 16. Перечитать конфигурацию BIND

**Зачем: Просим работающий BIND перечитать проверенные настройки и зоны, чтобы опубликовать изменения.**

```bash
sudo rndc reload
```

Ожидаемый вывод и результат:

```text
server reload successful
```

## Шаг 17. Изменить или проверить правило firewall

**Зачем: Сохраняем разрешение DNS в выбранной внутренней зоне firewalld для клиентских запросов.**

```bash
# Выберите firewall-ветку
sudo firewall-cmd --permanent --zone=internal --add-service=dns
```

## Шаг 18. Изменить или проверить правило firewall

**Зачем: Применяем постоянные правила DNS-доступа в firewalld, чтобы клиенты могли обращаться к серверу.**

```bash
# Выберите firewall-ветку
sudo firewall-cmd --reload
```

## Шаг 19. Проверить DNS-запись

**Зачем: Запрашиваем SOA без рекурсии, чтобы подтвердить авторитетность ответа и актуальный serial загруженной зоны.**

```bash
# 192.168.10.53 — адрес DNS-сервера
# UFW — альтернатива: разрешите от 192.168.10.0/24 TCP/53 и UDP/53
dig @192.168.10.53 example.test SOA +norecurse
```

Ожидаемый вывод и результат:

```text
<имя>. <TTL> IN <тип> <ожидаемое значение>
```

## Шаг 20. Проверить DNS-запись

**Зачем: Проверяем авторитетный A-ответ без рекурсии, чтобы подтвердить загрузку локальной прямой зоны.**

```bash
# 192.168.10.53 — адрес DNS-сервера
dig @192.168.10.53 www.example.test A +norecurse
```

Ожидаемый вывод и результат:

```text

```

## Шаг 21. Проверить DNS-запись

**Зачем: Проверяем MX-запись без рекурсии, чтобы подтвердить опубликованный маршрут почты для учебного домена.**

```bash
# 192.168.10.53 — адрес DNS-сервера
dig @192.168.10.53 example.test MX +norecurse
```

Ожидаемый вывод и результат:

```text
<имя>. <TTL> IN <тип> <ожидаемое значение>
```

## Шаг 22. Проверить DNS-запись

**Зачем: Проверяем обратное разрешение адреса в имя, чтобы подтвердить загрузку PTR-зоны.**

```bash
# 192.168.10.53 — DNS-сервер; 192.168.10.20 — файловый сервер
dig @192.168.10.53 -x 192.168.10.20 +norecurse
```

Ожидаемый вывод и результат:

```text
<имя>. <TTL> IN <тип> <ожидаемое значение>
```

Каждый authoritative ответ содержит флаг aa и ожидаемые данные.
